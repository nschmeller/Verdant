# Verified API / Feasibility Claims

_Generated by the design workflow (13 agents). Each claim adversarially fact-checked against primary Apple sources._

## [CONFIRMED] Apple Foundation Models on-device base model has a limited context window (a few thousand tokens, shared across input+output), and exceeding it throws a recoverable error requiring a fresh session or a condensed transcript.

All four components verify against primary Apple sources. (1) Size: Apple's Technote TN3193 and Apple DTS engineer Ziqiao Chen both state the on-device SystemLanguageModel has a context window of 4096 tokens per session; Apple staffer "MB-Researcher" calls it a fixed limit, and a separate DTS reply approximated it as "around 4,000" — so "a few thousand tokens" is accurate (precisely 4096, not a vague estimate). (2) Shared input+output: confirmed verbatim by the DTS engineer — "all the input and response in the generation process contribute tokens to the context window," and the flexible split is illustrated (4000 input tokens leaves ~96 for output). (3) Error: overflow throws LanguageModelSession.GenerationError.exceededContextWindowSize (the GenerationError type is deprecated as of 26.4 in favor of LanguageModelSession.Error, but the case name persists). (4) Recovery: TN3193's prescribed approach is to trim/summarize the transcript and start a new session — the overflowed session itself cannot continue, so a fresh session (optionally seeded with a condensed transcript) is required. Caveat noted by Apple: the token count printed in the error reflects the moment overflow was detected (e.g., 4090 or 4100), but the true ceiling is always 4096. As of iOS/macOS 26.4, SystemLanguageModel.contextSize and tokenCount(for:) let apps measure this at runtime rather than hardcoding it, and the separate Private Cloud Compute model has a 32k window — but the on-device base model is 4096.

**Architectural implication:** The architecture must treat the on-device session as a small, exhaustible buffer (~4096 tokens covering instructions + accumulated transcript + injected @Generable schemas + tool definitions + prompt + the generated output). Concretely: (a) feed compact derived summaries/facts, never raw HealthKit time-series; (b) keep @Generable types and @Guide text lean and minimize concurrent tool definitions, since schemas are injected into the prompt and consume budget; (c) proactively budget using contextSize/tokenCount(for:) on 26.4+ and trigger condensation around 70-80% capacity rather than waiting for the throw; (d) build an explicit session-rotation path: on exceededContextWindowSize (or proactively), summarize the prior transcript via a separate session and rehydrate a fresh LanguageModelSession with that summary; (e) do NOT hardcode 4096 — query contextSize at runtime so the app adapts if Apple ships a larger on-device window or you route to the 32k Private Cloud Compute model.

Sources: https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window · https://developer.apple.com/forums/thread/806542 · https://developer.apple.com/forums/thread/790736 · https://developer.apple.com/documentation/foundationmodels/languagemodelsession/generationerror/exceededcontextwindowsize(_:) · https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/contextsize

## [CONFIRMED] Apple Foundation Models supports guided generation (@Generable typed output) and tool calling (the Tool protocol) fully on-device with no network.

Apple's primary docs confirm every element. (1) On-device: the framework "gives you access to the on-device Large Language Model that powers Apple Intelligence" and "runs on-device... without requiring network connectivity for inference." (2) Guided generation: the @Generable macro lets you "define custom data structures and the framework provides strong guarantees that the model generates instances of your type," implemented via constrained sampling/decoding executed by an on-device OS daemon. (3) Tool calling: the Tool protocol defines "a tool that a model can call to gather information at runtime or perform side effects," and Apple states tool calling "builds on guided generation" so the model "will never produce invalid tool names or arguments." All three are features of the same on-device SystemLanguageModel.default; inference (including the constrained decoding backing both Generable and Tool calling) runs locally on the Neural Engine with no server round-trip. Two precise caveats refine but do not refute the claim: (a) Tool.call(arguments:) is YOUR code and MAY itself hit the network -- Apple's own example says a tool "searches a local or online database." The model/inference is on-device; what a tool does internally is the developer's choice. (b) Apple offers a SEPARATE opt-in path, Private Cloud Compute / PrivateCloudComputeLanguageModel, "when you need more reasoning capabilities and context size" -- that is a different model object that does use Apple servers, but it is not the default and not what the claim refers to. Availability is also gated on Apple-Intelligence-capable hardware with Apple Intelligence enabled.

**Architectural implication:** You can architect a genuinely zero-cloud health app: drive @Generable typed extraction/classification and Tool-protocol orchestration entirely against SystemLanguageModel.default with no network dependency and no per-call cost, satisfying the privacy requirement. Two design rules follow from the caveats. First, the on-device guarantee covers the model, not your tools -- if any Tool's call(arguments:) reaches an online database it reintroduces a network path, so keep tool bodies local (SwiftData/HealthKit queries) to preserve the zero-cloud property. Second, do NOT reach for PrivateCloudComputeLanguageModel as a convenience fallback for hard reasoning, since that routes data to Apple servers and breaks the no-network guarantee; instead degrade gracefully on-device and gate everything on SystemLanguageModel availability, since unsupported hardware has no local model at all.

Sources: https://developer.apple.com/documentation/foundationmodels · https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models · https://developer.apple.com/documentation/foundationmodels/tool · https://developer.apple.com/videos/play/wwdc2025/301/ · https://www.apple.com/newsroom/2025/09/apples-foundation-models-framework-unlocks-new-intelligent-app-experiences/

## [PARTLY] On-device Foundation Models inference can be invoked from within a BackgroundTasks BGProcessingTask, subject to that task's time/compute budget, enabling periodic background analysis.

The mechanical core is CONFIRMED by primary sources. (1) Apple's official docs designate BGProcessingTaskRequest as the primitive for "deferrable, long-running processing tasks... such as when the device is charging... great for tasks like running machine learning" (developer.apple.com/documentation/backgroundtasks/bgprocessingtaskrequest and /performing-long-running-tasks-on-ios-and-ipados). The task runs only until its time/compute budget is exhausted, at which point the expirationHandler fires and you must call setTaskCompleted. (2) On the Apple Developer Forums (thread 798113), an Apple Staff engineer states on the record: "You can run a Foundation Model session in a background process, but on the operating-system level background calls to the on-device model are rate limited. This is because... currently all inference against the on-device model runs serially one at a time, and the model is a shared resource across the operating system." DTS engineer Ziqiao Chen adds the inference "will eventually run on the neural engine serially." So invoking LanguageModelSession inside a BGProcessingTask is explicitly supported. Why only PARTLY, not fully confirmed: the claim's framing that it merely "is subject to that task's time/compute budget" is incomplete and somewhat misleading. There is a SECOND, independent governor Apple calls out explicitly — an OS-level rate limit on background model calls (surfaced as LanguageModelSession.GenerationError/LanguageModelError .rateLimited) that exists regardless of how much budget your BGProcessingTask has. You can be inside a healthy multi-minute processing window and still be throttled or rejected because the ANE is a serialized, system-shared resource. Additionally, "enabling periodic background analysis" overstates reliability: BGProcessingTask is opportunistic/best-effort (system schedules it based on charging, thermal state, and learned app-usage; it will not run at all if the user force-quits the app, and is not a guaranteed periodic timer). I could not pull the rendered text of the .rateLimited documentation page directly (developer.apple.com pages render client-side and WebFetch returned only the title), so that specific API description is corroborated via the forum and secondary sources rather than read verbatim — a minor evidentiary gap, but the engineering claim itself is on the record from Apple Staff.

**Architectural implication:** Architecturally viable but do NOT design it as a reliable cron-like "analyze every N hours" pipeline. Treat the BGProcessingTask as an opportunistic trigger, not a guaranteed worker: set requiresExternalPower = true (greatly improves the chance the system grants the multi-minute window, and is appropriate for ANE-heavy work), always reschedule the next BGProcessingTaskRequest from inside the running handler BEFORE setTaskCompleted, and install an expirationHandler that checkpoints partial results so work resumes rather than restarts. Critically, budget for TWO limits, not one: the task's wall-clock/compute budget AND the OS-level background rate limit on the model. Wrap every respond/streamResponse in a catch for .rateLimited with exponential backoff and a foreground fallback (e.g., finish deferred inference at next app launch). Do bounded inference per wake (a few short summarize/extract/classify calls — consistent with the ~4096-token window and ~30 tok/s throughput), persist each result to your SwiftData insight log immediately, and never assume foreground-speed throughput or guaranteed scheduling. Consider an HKObserverQuery + enableBackgroundDelivery trigger to ENQUEUE a BGProcessingTask (rather than running heavy inference in the brief observer wake), and gate everything on SystemLanguageModel availability since the device may be ineligible or the model still downloading.

Sources: https://developer.apple.com/forums/thread/798113 · https://developer.apple.com/documentation/backgroundtasks/bgprocessingtaskrequest · https://developer.apple.com/documentation/BackgroundTasks/performing-long-running-tasks-on-ios-and-ipados · https://developer.apple.com/documentation/foundationmodels/languagemodelsession/generationerror/ratelimited(_:) · https://developer.apple.com/videos/play/wwdc2025/227/

## [CONFIRMED] HealthKit can wake an app in the background via HKObserverQuery + enableBackgroundDelivery, and incremental new data can be fetched with HKAnchoredObjectQuery using a saved anchor.

All three components are confirmed against primary Apple sources. (1) Background wake: An HKObserverQuery whose type has enableBackgroundDelivery(for:frequency:withCompletion:) turned on causes HealthKit to launch/wake a suspended app when matching samples are written or deleted. This requires the com.apple.developer.healthkit.background-delivery entitlement ("indicates whether observer queries receive updates while running in the background"), and HealthKit launches the app for the enabled types. (2)+(3) Incremental fetch via saved anchor: HKAnchoredObjectQuery returns added samples AND deleted objects plus a new HKQueryAnchor; Apple states an anchor "represents a specific point in time in the evolution of the health database... When you provide HealthKit with this anchor, HealthKit will only return the changes since that point." The documented pattern is exactly to persist the returned anchor and pass it back on the next query to get only new/changed data. Important bounding caveats (none of which refute the claim): the background wake gives only a SHORT run window, you MUST call the HKObserverQueryCompletionHandler or the system kills the app and eventually stops sending background updates, the entitlement is required, frequency is a hint the system can throttle, and force-quit suppresses delivery. I could not extract the rendered body text of the Apple doc pages directly via WebFetch (they are client-side rendered), so confirmation rests on Apple's indexed doc content, the entitlement doc, the WWDC20 'Synchronize health data with HealthKit' session (which shows the exact anchored-query handler signature and the persisted-anchor flow), and Apple DTS forum guidance — all mutually consistent.

**Architectural implication:** This validates the intended trigger backbone: use HKObserverQuery + enableBackgroundDelivery purely as an event-driven wake, and HKAnchoredObjectQuery with a persisted HKQueryAnchor as the incremental delta source so you only process new/deleted samples. Critically, the wake is a brief, throttleable window with a mandatory completion handler, so do NOT run Foundation Models LLM inference inside the observer callback (background on-device model calls are OS rate-limited and the window is too short). The correct shape is: observer wakes app -> run anchored query to pull deltas -> persist the new anchor and the raw deltas to local store (SwiftData) -> enqueue a BGProcessingTask (ideally requiresExternalPower) or defer to next foreground for the heavy LLM analysis -> call the observer completion handler immediately. Persist the anchor durably (it is the resumable cursor) and gracefully handle background delivery being throttled, the app being force-quit, and the completion handler being missed.

Sources: https://developer.apple.com/documentation/healthkit/executing-observer-queries · https://developer.apple.com/documentation/HealthKit/HKHealthStore/enableBackgroundDelivery(for:frequency:withCompletion:) · https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.healthkit.background-delivery · https://developer.apple.com/documentation/healthkit/hkobserverquery · https://developer.apple.com/documentation/healthkit/hkobserverquerycompletionhandler · https://developer.apple.com/documentation/healthkit/hkanchoredobjectquery

## [CONFIRMED] Foundation Models inference, HealthKit reads/aggregation, SwiftData persistence, and NLEmbedding-based semantic search can ALL run fully on-device with zero cloud calls.

All four components can run fully on-device with zero network round-trips, confirmed against primary Apple sources. (1) Foundation Models: Apple states the framework's model "runs on-device, so all data going into and out of the model stays private... it can run offline." The framework exposes ONLY the on-device ~3B model via SystemLanguageModel.default (WWDC25 session 286). The server-scale model is a SEPARATE, explicitly-adopted API (PrivateCloudComputeLanguageModel, added 26.4); it is never invoked implicitly by the on-device path, so zero-cloud holds as long as you do not adopt it. (2) HealthKit: HKHealthStore reads and statistics/aggregation queries operate on the device's local health database; reads do not call a server. (3) SwiftData: persists to a local SQLite store and is fully offline-capable — IMPORTANT CAVEAT: it defaults to syncing with the user's private CloudKit database, so you MUST set ModelConfiguration(cloudKitDatabase: .none) to guarantee zero cloud. (4) NLEmbedding (classic .sentenceEmbedding/.wordEmbedding) uses built-in, on-device language models with no network; you compute vector(for:) and run your own cosine search locally. Adversarial note on embeddings: NLContextualEmbedding (the higher-quality transformer alternative) downloads model ASSETS from Apple on first use via requestAssets — that is a one-time asset fetch from Apple, not the user's data leaving the device, and once present it resolves with no network activity; but the claim specifically named NLEmbedding, which has no such download. The Foundation Models framework itself exposes NO embeddings API, so the embedding layer is correctly NaturalLanguage, not Foundation Models. Confidence is high for FM, NLEmbedding, and HealthKit; the only genuine 'gotcha' is SwiftData's CloudKit-on-by-default behavior, which is a configuration choice, not a hard limitation.

**Architectural implication:** A zero-cloud, offline, privacy-preserving health-insight architecture is viable end-to-end: FoundationModels for on-device LLM summarization/extraction, HealthKit for local reads/aggregation, SwiftData (local-only) for the insight store, and NLEmbedding for a hand-rolled local vector store + cosine search. Three architectural guardrails are mandatory to actually realize 'zero cloud': (a) set SwiftData ModelConfiguration(cloudKitDatabase: .none) and a local-only store — do not enable CloudKit/.automatic; (b) do NOT adopt PrivateCloudComputeLanguageModel, since that is the one Foundation Models path that leaves the device; (c) if you switch from NLEmbedding to NLContextualEmbedding for quality, account for a first-run on-device asset download from Apple (gate on hasAvailableAssets/requestAssets) — the embeddings themselves stay local but the model binary is fetched once. Also gate on FM availability (deviceNotEligible/appleIntelligenceNotEnabled/modelNotReady) and provide a non-FM fallback, since on unsupported devices the LLM layer is simply absent. Net: the 'fully on-device, zero cloud' design is sound, contingent on these explicit configuration choices rather than defaults.

Sources: https://developer.apple.com/videos/play/wwdc2025/286/ · https://developer.apple.com/documentation/foundationmodels · https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel · https://machinelearning.apple.com/research/introducing-apple-foundation-models · https://developer.apple.com/documentation/naturallanguage/nlembedding · https://developer.apple.com/documentation/naturallanguage/nlembedding/sentenceembedding(for:revision:)

## [CONFIRMED] Foundation Models requires iOS 26+ on an Apple-Intelligence-capable device with Apple Intelligence enabled, and availability must be checked at runtime before use.

All three sub-claims are confirmed against Apple's primary documentation (the developer.apple.com documentation JSON API for SystemLanguageModel and SystemLanguageModel.Availability). (1) OS requirement: SystemLanguageModel and its Availability enum are marked iOS 26.0+, iPadOS 26.0+, macOS 26.0+, visionOS 26.0+, Mac Catalyst 26.0+ (watchOS 27.0 beta). So 'iOS 26+' is correct as the iOS floor; note the framework spans multiple OSes, not iOS alone. (2) Device + Apple Intelligence: the entry point is SystemLanguageModel.default, and availability resolves to .unavailable(.deviceNotEligible) when the hardware cannot run Apple Intelligence and .unavailable(.appleIntelligenceNotEnabled) when the user has not turned Apple Intelligence on in Settings — directly confirming both the 'Apple-Intelligence-capable device' and 'Apple Intelligence enabled' requirements. Apple's own sample code switches over model.availability. (3) Runtime check: Apple's documented pattern is to read model.availability (an Observable property; also the isAvailable convenience) and switch over .available vs .unavailable(reason) before creating a LanguageModelSession. A third transient reason, .modelNotReady (assets still downloading), reinforces that availability genuinely varies at runtime and cannot be assumed. One nuance, not a defect in the claim: Apple does not publish a hardware eligibility list inside the framework reference itself (the specific device list — iPhone 15 Pro/Pro Max, all iPhone 16, A17 Pro/M-series iPads, M-series Macs, Vision Pro — comes from Apple Intelligence support pages, not the FoundationModels API docs). The API expresses 'capable device' abstractly via .deviceNotEligible rather than enumerating models.

**Architectural implication:** Treat Foundation Models as a conditional capability, never a guaranteed one. Architecturally you must: (a) gate every code path on a runtime check of SystemLanguageModel.default.availability and switch over all unavailable reasons; (b) ship a non-LLM fallback for .deviceNotEligible and .appleIntelligenceNotEnabled (these are not recoverable in-app — base iPhone 15 / iPhone 14 and older get zero access even on iOS 26), which for a health-insight app means a deterministic, rules-based or on-device-ML alternative; (c) handle .modelNotReady as transient (show progress, retry, and because SystemLanguageModel is Observable, let SwiftUI re-render when it flips to .available); and (d) set the deployment target to iOS 26 for the feature (or weak-link/availability-guard it behind #available if the app supports earlier iOS). Do not gate on a hardcoded device-model list — rely on the framework's .deviceNotEligible signal, since the eligible-hardware set lives outside the API and can change.

Sources: https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel · https://developer.apple.com/documentation/foundationmodels/systemlanguagemodel/availability-swift.enum · https://developer.apple.com/documentation/foundationmodels · https://developer.apple.com/documentation/foundationmodels/languagemodelsession


## [UNVERIFIED] `HKStatisticsQuery(.cumulativeSum)` over a plain date predicate sums samples from EVERY source, so a phone paired with a Watch double-counts step count unless sources are merged.

Not fact-checked against Apple sources — recorded here because it is exactly the kind of claim this
document exists to settle, and because the code currently assumes the favourable answer without
saying so. What is known from this codebase rather than from Apple: the CATEGORY path already solves
the same problem explicitly. `SleepAggregation.mergedSeconds` clamps and merges overlapping intervals
"so overlapping stages or multiple sources (Watch + phone) aren't double-counted", and its tests
cover identical and containing intervals from two devices. The QUANTITY path does a raw
`cumulativeSum` with no equivalent. That asymmetry is evidence that multi-source duplication was
considered for one path and not the other; it is not proof that the other needs it, since HealthKit
may aggregate quantities differently.

**Architectural implication if TRUE:** step count — the app's most prominent metric — is inflated for
every user with a paired Watch, and every statistic, finding and card built on it inherits the error.
No downstream safeguard can detect it: the numbers are internally consistent, just wrong. The fix
would be an `HKSourceQuery` to pick a preferred source, or Apple's own merged-source behaviour if one
exists.

**How to settle it (about five minutes, needs a real paired device):** open the Health app, note a
day's step total, then compare against the rollup Verdant stored for the same civil day. Equal means
HealthKit is already merging and nothing needs to change; roughly doubled means it is not. Do NOT
change the ingest speculatively — a wrong de-duplication would discard legitimate multi-device data,
which is worse than the inflation it tries to fix.

## [UNVERIFIED] A SwiftData store written with `.completeUnlessOpen` cannot be OPENED by a `BGProcessingTask` that launches while the device is locked.

Apple's documented semantics for `.completeUnlessOpen` are that a file may be opened only while the
device is unlocked, and stays readable afterwards if it was already open. What is not verified here
is the consequence for this app's specific case: a background task that launches a FRESH process at
3am on a charging, locked phone, and must therefore open the store from scratch. The simulator does
not enforce data protection, so it cannot be observed from the test suite.

**Architectural implication if TRUE:** `VerdantApp` falls back to an in-memory container when the
store will not open. That is right for a foreground launch (a usable session beats a refusal to
start) and wrong for a background one: the pass would reason over an EMPTY history and write its
findings, journal and anchors into a store that evaporates when the task ends — a whole granted
on-power window spent producing nothing, with no error raised.

**Already guarded, whatever the answer.** `AppModel.storeIsEphemeral` records the substitution and
both background arms yield the window immediately when it is set, so the app cannot burn a window on
a store whose writes are discarded. The guard is conditioned on a fact the app KNOWS (the fallback
happened), not on this claim, so it is correct either way.

**How to settle it:** lock a charging device overnight with the enhancement task scheduled, then
check on unlock whether the run recorded itself (`BackgroundRunDiagnostics.stampEnhance`) or whether
the store opened at all. If the open succeeds while locked, the ephemeral guard simply never fires.

## [CONFIRMED] The safety panel's unanimity rule drops findings four of five reviewers cleared

The full pipeline was run twice against the real on-device model — the first time anything had. The
second run seeded five metrics with real structure (a sleep to resting-heart-rate link, a regime shift,
weekend patterns in steps and energy) and ran 645 seconds.

It kept nothing, and this time the feed said why:

    ✗ Dropped "Weekend Energy Surge Tied to Resting Heart Rate Dip" — the safety panel couldn't confirm it
    · Safety reviewer 5/5: clear
    · Safety reviewer 4/5: clear
    · Safety reviewer 3/5: flagged
    · Safety reviewer 2/5: clear
    · Safety reviewer 1/5: clear

Four of five reviewers cleared a benign wellness observation. One flagged it. The finding died.

**This is the design, not a bug.** `passesSafety` requires a majority to render AND every rendered
verdict to say safe, because a false negative on a health app's prose is worse than a lost finding,
and `SafetyVerdict`'s own guide says "when in doubt, false". Five independent reviewers each told to
err toward false will, between them, flag benign text at some rate — and the panel is unanimous, so
that rate is the rate at which good findings are lost.

What is newly known is that the rate is not negligible: the ONE finding that reached the panel in a
realistic run was killed by a lone dissent.

**For the owner, not for me to change.** Loosening a safety gate is a product and liability decision.
The options, none taken: keep unanimity (safest, loses findings); require a majority of safe verdicts
(matches the skeptic panel); or keep unanimity but let the flagged reviewer's concern be re-examined.

**What was changed** is that the panel is now diagnosable. A flagged reviewer's line names the concern
it was given, which costs nothing — the lens is already in hand, no schema field, no extra call — where
before the feed said only "flagged" and there was no way to learn which of the five fired or on what
grounds, on the gate that decides whether anything reaches the user at all.


## [CONFIRMED] Excluding untestable re-tests works, and the vetting stack rejects a genuine finding

Three probes put the same well-supported claim — a 4 bpm resting-heart-rate regime shift, with its
real verified basis — to the panels against the real on-device model. The third used realistic
day-to-day spread (effect size 2.0 SD, where the first two had an implausible 8.2).

    run              skeptics    replication              safety
    clean data       4/10 held   0/5 held ("No data…")    refused
    clean + fixes    3/10 held   0/5 held ("No data…")    —
    realistic data   2/10 held   0/0 — PASSED             refused

**The `couldTest` change is verified.** Before it, analysts that could not obtain data answered "when
in doubt, false" and the panel scored 0 of 5 — a refutation of a true claim by analysts who never
tested it. After, those verdicts are excluded and the panel falls open at 0/0. The underlying
inability is unchanged (no analyst managed a re-test in any run); what changed is that it no longer
counts as evidence against.

**A hypothesis that was wrong, recorded because it shaped two fixes.** The 8.2 SD effect looked
implausible, and a skeptic had rejected the finding saying so — suggesting the fixture was at fault.
With realistic noise the skeptics did WORSE (2/10), and for a confabulated reason: "this finding is
trivial because it is essentially a restatement of the fact that your heart rate typically increases
during exercise and decreases after exercise." The claim says nothing about exercise. Effect size was
never the cause.

**Three runs, three different datasets, and the finding never survived.** Skeptics rejected it every
time (2–4 of 10 holding, against a strict-majority bar), and safety refused benign prose every time it
was asked. This is the app's own bar working as specified — no test is failing — but on this evidence
a genuine finding does not reach a feed.

**For the owner.** The calibration of both panels is a product decision: how hard should a real
finding have to work? The measurements are here; the options for safety are in the entry above; for
the skeptic panel the equivalent question is whether a strict majority of ten adversarial lenses,
each told "when in doubt, false", is the intended bar. Nothing has been changed on either.
